Analysis only. Nothing in the code was changed. Audited revision `0ee7022`.

- **[code]** an auditor read the code path and cited the line; lines I opened myself are marked **[code, checked]**.
- **[docs]** a research agent opened the vendor's page or source and quoted it. I did not reopen it.
- **[unverified]** inference, a forum post, or a page that could not be opened.

Who did what: three Opus (medium) code audits, two Opus (high) web research jobs, one independent Codex `gpt-6.2-sol` xhigh audit with no hypotheses given (`codex-0b461e52`), and my own measurements. Codex then reviewed this document; its objections are in [section 9](#9-codexs-review-of-this-document).

## 1. Bottom line

1. **Visibility does not need the Haiku wrapper.** Every host has a zero-token surface the bridge is not using: MCP tasks and the status line in Claude Code, a status-line script in Antigravity, an experimental status-line provider in Codex. The bridge sends no progress notifications, serves no MCP tasks and has no command besides "start the server" [run].
2. **One thing shown today is not true.** For Codex jobs the `model` field is the model that was requested, or the one in `config.toml`, or the literal `codex-default`. The bridge never reads back what ran [code, checked: `runners.py:1993`]. Fix this before putting the model on screen.
3. **A waiting call is the weak point.** `run_agent` waits for the whole job by default [code, checked: `jobs.py:1568`]. Codex stops a tool call at 60 s by default, and Cursor's CLI does too and cannot be raised [unverified, forum]. When the host gives up, the caller has no job id, and whether the job then stops or runs on is not reliable either way (finding 2).
4. **Two audits agree on the same core failure list**: a batch that half-starts and loses its job ids, a broken Codex or `agy` stream reported as `completed`, replies with no size cap, owner liveness with no time limit, and `read_only` on `agy` that is an instruction while the tool is annotated read-only.
5. **"Lighter" is mostly about what the host model carries, not lines of code.** The nine tool schemas are about 4,200 tokens, and one planning call returns the same quota data three times. The code can lose roughly 1,000 to 1,500 of 13,700 lines; it is not bloated, it is concentrated in three files of 2,000+ lines.
6. **As a product, install is the wall.** Sixteen manual steps across three hosts, a 939-line README that is half reference and half lab notebook, no CI. A console script already exists in `pyproject.toml` and is unused.

### MCP tasks in Claude Code: probed [run]

After the review, a throwaway server (one tool, an `Extension` on SDK 2.3.0 returning a plain dict) was run against Claude Code 2.1.332 in a headless streaming session (`--input-format stream-json` with `CLAUDE_AUTO_BACKGROUND_TASKS=1`; a one-shot `claude -p` does not get tasks). What happened:

- Claude Code sent `server/discover` and declared `io.modelcontextprotocol/tasks` on the `tools/call`, on protocol 2026-07-28. Its client name on the wire is `claude-code`.
- The call came back at once as a background task. Claude Code polled `tasks/get` every 2 seconds and showed each `statusMessage` as the task's live summary.
- The task's label is `<server>/<tool>` (`taskprobe/slow_job`), not the task id. So backend, model, effort and label belong at the front of `statusMessage`, which is what identifies a row.
- On completion the result was delivered to the model as a task notification and Claude answered with it. No polling by the model, no wrapper agent, no tokens while waiting.
- Stopping the task sent `tasks/cancel` to the server, twice, without waiting for an answer. The handler must be idempotent.

Still not seen: the `/tasks` panel itself in an interactive terminal. The data it is given is the label and summary above.

### What to build, in order

1. **One status string, built in one place.** `codex · gpt-6.2-sol · xhigh · running 2m10s · reading jobs.py`. Every other item reuses it. Needs a `last_activity_at` column: today `last_activity` has no timestamp, and a best-effort progress write that hits a lock is dropped with only a debug log [code: `jobs.py:925-949`]. A reader of the database sees committed state only: status turns `running` before setup, model and activity are best-effort, and the default effort often arrives only when the job ends. So the line must show when each value was last seen, and say `unknown` where it is.
2. **`agent-bridge status`** with `--line`, `--watch` and `--json`, reading `bridge.db` read-only. `python -m agent_bridge` with no argument must keep meaning "serve", and the command must open the database with SQLite's `mode=ro`, never through the bridge's own store class, which migrates, registers an owner and recovers jobs. This one command gives the status line in Claude Code and Antigravity and the second pane for Codex. Low effort. Your status line is already a PowerShell script; it would call this command.
3. **MCP tasks**, offered only when the request declares the tasks extension. Named row, live message, real cancel mapped to `cancel_job`. This is the piece closest to "how Claude's own agents look", and it also fixes "stopping the agent does not stop the job". Medium to high effort: the SDK's built-in task types are an older wire contract, so the extension is written against the 2026-07-28 tasks specification (`tasks/get`, `tasks/update`, `tasks/cancel`), and `tasks/get` needs a read path that does not write, which `get_async` is not today. Claude Code only today; Codex and Antigravity never ask for it, so they are unaffected.
4. **Progress notifications** from `run_agent` and a waiting `check_jobs`, carrying the status string. Worth it for a second reason: a stdio call that sends no response and no progress for 30 minutes is aborted by Claude Code [docs]. Copilot CLI draws them and extends its timeout on them [docs].
5. **A slim wrapper agent file**, for people who want the agent-list row anyway: `~/.claude/agents/bridge-job.md` with `model: haiku`, `tools` limited to `start_agent` and `check_jobs`, and `omitClaudeMd: true`. Should remove most of the roughly 40k fixed start-up [unverified projection: run one job and measure]. A longer poll is not the saving: this session's second wrapper polled at 280 s and used 57,000 tokens over 4 calls, against 55,800 over 12 calls for the first at 90 s [run]. The fixed start-up is what costs.
6. **Label the Codex model honestly** (`requested: gpt-6.2-sol`). Codex 0.172.0's `exec --json` events carry no model field, so there is nothing to read back today [docs, Codex checked the tagged source]. `agy` and Claude report theirs in the first stream event when the CLI includes it [code: `runners.py:1159`, `claude_runner.py:568`].

Also weak today: `agy`'s `last_activity` is only `"{step_type} ({state})"`, with no tool or command [code, checked: `runners.py:1185`]. Codex's shows the command text; Claude's shows the tool name.

## 3. What breaks

Ranked by severity times likelihood. "Both" means the Opus audit and the Codex audit found it independently.

| # | Finding | Where | Found by |
|---|---|---|---|
| 1 | **A batch can half-start and lose its ids.** Jobs are submitted one by one before the cancel handler is entered. A cancel or a failed insert on job 2 leaves job 1 running with no receipt. Codex confirmed it with an async stand-in | `jobs.py:1587` [code, checked] | Both |
| 2 | **A wait that the host gives up on ends badly either way.** `run_agent` waits for the whole job when `wait_seconds` is not given; `run_parallel` and `review_code` wait for the full timeout. If the host only stops waiting, the job runs on and the caller never got its id. If the host sends a cancel, the bridge tries to cancel the job, and in Codex's test through the SDK that cancel was itself interrupted at its first await, before the subprocess was told to stop. So the job is neither reliably kept nor reliably stopped. The existing test cancels a plain asyncio task, which does not exercise this | `jobs.py:1568-1577`, `1751`, `1784`; SDK `jsonrpc_dispatcher.py:640`; `test_runners_and_jobs.py:398` | Opus, corrected by Codex |
| 3 | **A broken stream reads as success.** Codex needs no terminal event: exit 0 is `completed`. `agy` accepts a blank status and can take the last JSON object as its envelope. Only Claude fails a run with no result event. A CLI upgrade turns failures into completed jobs with junk replies | `runners.py:2217`, `1273`, `claude_runner.py:652` | Both |
| 4 | **`read_only` is not one guarantee.** On `agy` it is a sentence in the prompt; `review_code` is annotated `readOnlyHint=True` while it can launch that path. Codex and `agy` children inherit the whole environment, API keys and tokens included; only Claude has two keys removed | `runners.py:48`, `server.py:524-526`, `nesting.py:97-105`, `claude_runner.py:400` | Both |
| 5 | **Cancelling `agy` can clear the "prior turn may still be running" block.** The timeout path honours `agy`'s remote-turn signal; the cancel path raises before classifying it and records `stopped` from local cleanup alone. A later window may resume the session | `runners.py:1342`, `jobs.py:1267`, `storage.py:1735` | Codex |
| 6 | **A resume can edit the wrong checkout.** Turn A in a worktree, turn B relocated to the main checkout, then resume by A's job id: the old worktree comes back. Resume by session id goes to the main checkout | `jobs.py:289`, `373`, `691`, `718` | Codex |
| 7 | **No size limits.** Stdout and stderr are held in memory unbounded, and Codex and Claude parse stdout twice. The stored reply is cut at 200,000 characters with no flag. Replies to the host are never capped: `to_detail` supports a limit and no tool passes one. | 8 | **A failed final write strands the job.** Only lock errors are retried. On any other SQLite error the row keeps its previous state (queued or running), the claim stays held, and the reply lives in memory until the window closes | `jobs.py:824-854` | Both |
| 9 | **Owner liveness has no time limit.** An owner counts as live while its row has no exit time and its PID exists. The documented `AGENT_BRIDGE_OWNER_STALE_SECONDS` is discarded, so a hung bridge, or a PID reused by another program, holds a session claim for as long as that PID appears alive, and `cancel_job` refuses from any other window | `storage.py:189-198`, `1160`, `1182` [code, checked] | Both |
| 10 | **Failure classification reads the model's own prose.** Regexes such as bare `401`, `429`, `502` and "quota" run over text that, for `agy`, includes the reply. A false `transient_service` on a new read-only job is retried even after the first attempt made progress, which may spend quota twice. | 11 | **Two writers are not fenced.** A new turn that reveals a session id another job already holds writes that id and carries on without the claim. `finalize_job` updates by job id alone, so a late finalizer can overwrite an earlier terminal result | `storage.py:1577-1621`, `1656-1667`, `jobs.py:997`, `1805` | Codex |
| 12 | **Pruning and resume.** The 500-job cap counts queued and running rows, so active jobs can push finished results out. A pruned or mistyped job id passed as `resume_from` is forwarded to the CLI as a session id | `storage.py:1767`, `jobs.py:310` | Codex, Opus |
| 13 | **A subagent's reply is handed to a more privileged host as plain tool data.** An untrusted repository can shape a reply that asks the host to run a command or grant edit access; what happens next depends on the host. A nested bridge can also read other windows' prompts and replies through `check_jobs` | `models.py:241-245`, `server.py:239`, `484` | Codex |
| 14 | **Waiting competes with working.** A cross-window `check_jobs` wait runs a write transaction about five times a second; a queued resume tries the session claim about eight times a second. Each opens a new connection | `jobs.py:631`, `683`, `1707-1728`, `storage.py:586` | Both |

### What the host model carries [run]

| Item | Size |

| `usage_dashboard` | 8.5 KB, of which the view the user reads is 1.15 KB |
| Job replies | All but `start_agent` and `cancel_job` carry `session_usage` (the window's totals, easily read as the job's). Full details carry `owner_id`, and `cwd` plus `effective_cwd` even when equal. Attempts appear twice on a retry [code: `models.py:198-274`, `storage.py:1650`] |

Cuts, in order of value:

1. **One quota shape**, about 2.5 KB: per pool the 5 h and weekly percent left, reset and priority, then the order and any read error. Saves about 1,400 tokens on each planning call. `get_usage`, the dashboard and `list_backends` embed it.
2. **Cap replies and page them.** Default the reply text to a few thousand characters with `response_truncated` and an offset on `check_jobs`. Finding 7.
3. **Five tools instead of nine.** `run(tasks[], wait_seconds=0)`, `jobs` (list, wait, page), `cancel`, `usage` (quota and text opt-in), `backends`. `start_agent` is already `run_agent(wait_seconds=0)` [code: `jobs.py:1570`], and `review_code` is a prompt on top of `run_parallel`. What is lost: Codex's built-in `exec review`, unless it becomes a field on a task, and the dashboard skill's current call. A default of `wait_seconds=0` also takes most of the sting out of finding 2. Codex's caution: removing tools breaks the installed skill's fallback, the README's polling text and the handshake test that expects nine tools (`test_mcp_server.py:52`), so keep the old names as aliases for one release.
4. **Drop rare arguments** or fold them: `confirm_prior_stopped` (keep `confirm_prior_job_id`), `relocate_cwd`, `allow_cross_pool_fallback`, three `*_model` arguments into one map.
5. **Instructions that fit 512 characters first**, and then the pasted `CLAUDE.md` snippet can shrink to two or three lines.

## 5. A usable product

**Install.** Sixteen manual steps for three hosts: clone, sync, find the venv path, three registrations, three config edits (Codex timeout and approval, Antigravity timeout, Antigravity allow rule), three skill copies, two pasted snippets, three restarts.

- `pyproject.toml` already defines `agent-bridge = "agent_bridge.server:main"` [run]. The README registers the venv's Python instead. `uvx --from git+... agent-bridge` should work [unverified, not run].
- **`agent-bridge install --host <name>`**: write the host's MCP entry with the right timeout and approval keys, merging and never overwriting, with a `--print` dry run. Six config shapes cover every mainstream host [docs]. This touches files on the repo's ask-first list, so it shows a diff and asks.
- **`agent-bridge doctor`**: what `list_backends` checks, CLI version floors, each registration's path and timeout, one quota read per pool, the nesting check.
- The skill is not in the wheel (`pyproject.toml:26`); package it so `install` can copy it.

**README.** 939 lines. Proposed: about 120 lines (what it is, requirements, one install command per host, check it works, five example requests, six lines on safety, links), with `docs/install.md`, `tools.md`, `backends-and-models.md`, `safety.md`, `quota-and-usage.md`, `troubleshooting.md`, `internals.md`, and a `verification-log.md` for the dated test runs now inline (README:109, 533-539, 595, 621, 705-707, 728-730, 760, 767, 883).

**Defaults and replies that bite.**

- 300 s timeout with a full wait. Default to background.
- `cwd` defaults to wherever the host started the bridge.
- `completed` with an empty reply. Fail it, or flag it.
- `model: "codex-default"` reads as a model id.
- `elapsed_seconds` against `duration_seconds`; `usage` beside `session_usage`.
- A human first line in every result (the status string) helps every host, since Cursor, Codex, Antigravity and Gemini CLI hand the model the text part [docs].

**Drift found.** `AGENT_BRIDGE_OWNER_STALE_SECONDS` documented, no effect. README:818 says worktrees are for Codex; Claude gets them too. `list_backends(refresh_models=True)` also refreshes quota, undocumented. The version is 0.1.0 in two places, and `quota.py:839` sends "0.3.0" as its client identity to Codex's app server. Your global `CLAUDE.md` says three quota pools; there are four. Its 90 s poll is valid, and `check_jobs` allows up to 300 s.

What travels and what does not:

- **Server `instructions`** reach the model in Claude Code, Codex, Gemini CLI, OpenCode and probably Copilot. This is the portable channel for routing rules.
- **MCP prompts** would let the bridge ship `/bridge-usage` with no file copy, but Codex and Antigravity do not document them. Keep the skill files there.
- **`AGENTS.md`** is read by nearly every host; keep a five-line snippet as the fallback.
- **The Haiku-wrapper equivalent** exists everywhere as an agent file with a `model` field (`.cursor/agents`, `.gemini/agents`, `.agent.md`, `.opencode/agents`, Grok's `[subagents.models]`). With `agent-bridge status` none of them is needed for visibility.
- **Do not key behaviour on the client's name yet.** Log `clientInfo` on connect first; only three names are known.

### ACP

Every candidate speaks the Agent Client Protocol: `agy acp`, `gemini --acp`, `agent acp`, `opencode acp`, `copilot --acp`, `grok agent stdio` natively; Codex and Claude through adapters [docs]. For a new backend, one ACP client is cheaper than another JSON-stream parser, and the bridge would answer permission requests itself, which gives one real read-only mode [unverified inference]. It does not replace today's three runners: ACP reports context and cost, not per-turn tokens, and says nothing about quota.

### Prior art

PAL (zen-mcp), claude-code-router, codex-as-mcp, gemini-mcp-tool, claude-squad, Conductor [docs].
